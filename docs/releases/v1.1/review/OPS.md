# OPS review findings

Summary: 2 major, 4 minor. The ACL design is tight (no wildcards, one loopback-only super user, prefixes end in a separator, and CI compares the full listing exactly). The weak points are the hosted-migration runbook and a probe suite that can write into production topics.

## OPS-1 The hosted migration's env-file edit is lost on the next routine deploy  (major)
- Where: deploy/OPERATIONS.md:221-226, 240-241, 259-260, 270; deploy/operations/deploy.sh:19-20; deploy/operations/checkpoint.sh:9-13
- What: The runbook defines `$compose` with `--env-file /srv/lontra/current.env` and says to "Append `KAFKA_AUTHORIZATION=migrate` to the root-only env file" (later, "change the env file's line to `acl`"). It never says which file. `deploy.sh` rebuilds every candidate env from `stack.env` alone (`cat "$root/stack.env" > "$candidate"`, plus the image and config dir) and then promotes that candidate to `current.env`.
- Failure scenario: The operator edits `current.env`, which is the only edit `$compose ... up` will see, and finishes step 4 with `acl` verified. The next ordinary `deploy.sh <sha>` writes a new candidate from `stack.env`, which has no `KAFKA_AUTHORIZATION`, so `compose.yaml` falls back to `none`. Kafka is recreated with no authorizer and the deploy still reports "Healthy release". R2 is silently open again, while the deployment record and lab-api §10.7 say it is closed and hosted quarantine exercises may already be enabled. If the operator edits `stack.env` instead (the runbook only asks for a backup of it), step 2's `$compose up` doesn't change Kafka at all, and step 3 finds no "Kafka authorization" log line.
- Evidence: Inferred from reading deploy.sh, checkpoint.sh and OPERATIONS.md (no Docker here).
- Suggested fix: Say explicitly to set the line in `/srv/lontra/stack.env`, then run a deploy of the current SHA (or edit both files). Add a step-5 check that `current.env` and `stack.env` agree. Optionally, have `deploy.sh` refuse a candidate that lowers `KAFKA_AUTHORIZATION` compared with `current.env`.

## OPS-2 The ACL probe suite writes into the production creek topics when the broker isn't enforcing  (major)
- Where: deploy/test/kafka-acls.test.ts:55-81; deploy/test/kafka-acl-probes.mjs:116, 158, 162-165; documented for the host in deploy/OPERATIONS.md:261-266
- What: The config check (authorizer present, `allow.everyone.if.no.acl.found=false`) is one `test()`, and each principal's probes are separate `test()`s that run whether or not it passed. The probes then call `produce()` on every `field.*`, `creek.overview` and `field.notebooks` topic and expect "denied". When the broker isn't enforcing, those writes succeed and append `{"probe":…,"role":…}` records. Per `apps/field-station/src/kafka-handlers.ts:54-55`, the production gateway's handlers throw on a non-field-station record, which pauses the `field` (and `notebooks`) source at that record, and it is "never skipped".
- Failure scenario: Someone runs the documented host command (`STACK_KAFKA_EXEC="$compose exec -T" … kafka-acls.test.ts`) while the hosted broker is still at `none` (its default), for example to "check R2", or after a rollback. Test 1 fails, the gateway, field-station and bench probes still run, six junk records land in the production topics, and every live creek view and notebook stops until someone moves the consumer offsets by hand. lab-api.md:601 records exactly this kind of run on a standalone broker ("under `none` bench 1 failed 42 of its 45 probes"), so the writes really go through.
- Evidence: Reproduced that the probes run after the config check fails, using a fake exec that reports a broker without an authorizer:
  `STACK_KAFKA_EXEC=fake-exec.sh node --test deploy/test/kafka-acls.test.ts` printed `✖ the broker denies what no ACL allows…`, `✔ gateway can do only what its ACLs allow`, `✔ field-station can do only what its ACLs allow`, and the fake exec logged `PROBES WOULD RUN in gateway: env KAFKA_PROBE_BENCHES=1,2,3 node --input-type=module - gateway` (and the same for field-station). That the gateway then pauses is inferred from kafka-handlers.ts.
- Suggested fix: Read the broker properties in a `before` hook and skip or fail every probe test unless the authorizer is on with `allow.everyone.if.no.acl.found=false`. Belt and braces: have kafka-acl-probes.mjs refuse to start when a harmless denied check (for example `describe` of another principal's topic) is allowed.

## OPS-3 The runbook's description of `migrate` doesn't match how StandardAuthorizer behaves  (minor)
- Where: deploy/OPERATIONS.md:212-216 and 251-258; docs/contracts/lab-api.md:601 ("leaves operations nobody is granted (creating and deleting topics) open")
- What: `allow.everyone.if.no.acl.found` is decided per resource, not per operation. If any ACL matches the resource (which every `field.`, `creek.`, `lab-N.`, `streamotter-*` and `lontra-field-station-read-*` name now has), an ungranted operation is DENIED in `migrate` exactly as in `acl`. Operations that are let through because no ACL matches are logged at DEBUG only, and the authorizer logger is INFO, so they never show up in `kafka-authorizer.log`.
- Failure scenario: The runbook says `migrate` leaves "cluster operations, topic deletion, config reads" open and that "its use appears in the authorizer log instead of failing". In fact, under `migrate` a missing grant on any production topic or group (say a client starts calling DescribeConfigs or DeleteTopics on `field.gauges`) fails in production right away. A missing grant on an ACL-free resource (the cluster) is silently allowed and never logged, so step 3's "no 'is Denied' lines → safe to enforce" check can't catch it before step 4. `migrate` gives the operator neither of the two safety properties the runbook promises.
- Evidence: Apache Kafka 4.1.0 `StandardAuthorizerData.java`. `checkSection` sets `hasResourceAcls = true` for every ACL matching the resource, regardless of principal or operation (line 424). `MatchingRuleBuilder.build()` returns `noAclRule` only when `!hasResourceAcls` and otherwise returns DENY (lines 607-618). `logAuditMessage` logs ALLOWED only at debug/trace (lines 287-297), and `config/log4j2.yaml` sets `kafka.authorizer.logger` to INFO. Not run against a broker.
- Suggested fix: Describe `migrate` as "enforced on every resource that has a grant; open (and not logged) only on resources nobody is granted, such as the cluster and unprefixed topics", and correct lab-api.md:601. If an observation step is wanted, temporarily raise `kafka.authorizer.logger` to DEBUG during step 3.

## OPS-4 `--dir` accepts any git-ignored directory, including ones other tools own or Caddy serves  (minor)
- Where: scripts/dev-lab.mjs:180-191 (`localDirectory`), 297-299 (`prepare` stamps `dev-lab.json` into any existing directory), 455-483 (`discard`)
- What: The only rules are "inside the repo, git-ignored, not `.local` itself". `node_modules`, `dist`, `apps/site/dist/lab`, `.local/kafka-dev` and `apps/field-station/.data` are all accepted. `up` writes `dev-lab.json` into whatever is already there, so the "refuses to delete a directory the launcher did not make" guard (LOCAL_LAB.md:116) only protects directories where `up` has never run.
- Failure scenario: (a) `npm run dev:lab -- up --no-build --dir apps/site/dist/lab` writes `.env` (all stack secrets) and `secrets/` (Kafka CA key, origin key) into the directory Caddy serves at `/lab/`. Caddy's `file_server` serves dotfiles, so `https://localhost:8443/lab/.env` returns them (loopback only). (b) `up --dir .local/kafka-dev` followed later by `discard --yes` deletes dev:kafka's broker logs and checkpoints along with the Lab's files.
- Evidence: Reproduced the acceptance. `localDirectory()` returned a path, with no refusal, for `apps/site/dist/lab`, `node_modules`, `.local/kafka-dev`, `dist` and `apps/field-station/.data`. The serving and deletion consequences are inferred from reading `deploy/Caddyfile.local-lab` and `discard()`.
- Suggested fix: Require the directory to be under `.local/` and not `.local/kafka-dev` (or `LONTRA_KAFKA_DATA_DIR`). In `prepare`, refuse a non-empty directory that has no `dev-lab.json`.

## OPS-5 A bench probe claims to test another bench's group but uses a name in nobody's prefix  (minor)
- Where: deploy/test/kafka-acl-probes.mjs:159; docs/contracts/lab-api.md:548 (S12, "joining another bench's … group")
- What: The probe "read … in another bench's group" uses group `lab-<other>-acl-probe-<run>`. That name has no `streamotter-lab-<other>-` prefix, so it would be denied even if bench N were wrongly granted bench M's group prefix. The delete-group probe on line 167 does use the real prefix, and the exact-listing assertion catches extra ACLs today, so coverage isn't lost yet. The read probe itself proves nothing about cross-bench group isolation.
- Failure scenario: If the listing assertion were relaxed later (for example to "contains"), a grant like `streamotter-lab-` for every bench would still pass this probe.
- Evidence: Inferred from reading.
- Suggested fix: Use `streamotter-lab-${other}-acl-probe-${run}`.

## OPS-6 LOCAL_LAB.md leaves out the bench study volumes from stop/discard and miscounts services  (minor)
- Where: docs/LOCAL_LAB.md:32-33, 103-106, 174, 178-179, 232-234
- What: This PR adds `lab-1-state` to `lab-3-state` (each bench's `study.json`, journal and discarded-study summaries, per LC11-ADR-02) to compose.lab.yaml, which the local stack uses. The doc still says `stop` keeps "the Kafka log, the field station's checkpoints, Caddy's data volume", that the run "kept the three volumes", and that `discard` deletes "Kafka, checkpoint and Caddy volumes". There are six volumes, and the bench study state is exactly what "resumes the same study" depends on. Separately, the stack has 10 services, not "eleven" (line 174), and "the other ten containers" (line 33) should be nine.
- Failure scenario: A developer who wants a fresh bench study without losing the creek reads the doc, thinks the bench study lives in `.local/lab` or the field-data volume, and deletes the wrong thing, or doesn't know that `discard` also removes the bench study history.
- Evidence: Inferred from reading compose.lab.yaml:62-70 and 143-148 against the doc.
- Suggested fix: List the bench study volumes in the stop and discard text and the status paragraph, and correct the counts.

## Checked and found correct
- Kafka ACLs: no wildcard (`*`) resource or principal and no DENY entries. Every prefix ends in a separator (`field.`, `creek.`, `lab-N.`, `streamotter-lab-N-`, `streamotter-lontra-creek-`, `lontra-field-station-read-`), so `lab-1` can't match `lab-10`. The gateway's real groups (`streamotter-lontra-creek-field`, `-notebooks`), the bench groups (`streamotter-lab-N-<studyId>`) and the field station's read groups (`lontra-field-station-read-<uuid>`) all fall inside their grants.
- The super user is `User:ANONYMOUS` only. It comes only from the PLAINTEXT INTERNAL and CONTROLLER listeners bound to 127.0.0.1 inside the Kafka container. All other listeners are SASL_SSL, no service shares Kafka's network namespace (and shared-host config.mjs asserts no `network_mode`), and start.sh refuses a SCRAM user named ANONYMOUS.
- The idempotent producers need no cluster grant (KIP-679, probed for benches). The gateway (streamotter 0.1.0-rc.3) only uses `listTopics` and `fetchTopicMetadata` as admin operations, which `Describe` covers.
- The start.sh bootstrap: the awk parsing of `kafka-acls.sh --list` matches the 4.x format (checked against sample output). `kill -TERM $$` hits the exec'd broker. The ready file is removed at every start, and the health check waits for it. The grant count (13 with three benches, 4 without) matches the runbook.
- Ports: base compose publishes only Caddy's 443. The lab overlay publishes nothing. The local overlay `!override`s Caddy to `127.0.0.1:8443`. The CI spike overlay binds `127.0.0.1:9180` and `127.0.0.1:7500` only.
- Secrets: `.local/` is git-ignored. make-secrets.sh writes the env file mode 600 and never overwrites it. The image build context excludes `.local` (Dockerfile.dockerignore, and the copy used by `--extra-ca`). `--extra-ca` passes the CA as a BuildKit secret, never a layer.
- dev-lab: the prerequisite checks cover Node, Docker, the daemon, Compose ≥ 2.24.4, OpenSSL, `node_modules` and port 8443. `stop` is `down` without `--volumes`. `discard` requires `--yes` or the typed project name, refuses in a non-interactive shell, and deletes only `-p <project>` volumes and a directory that has `dev-lab.json`. The 23 unit tests pass, and `npm test` now includes `scripts/test`.
- CI: stack.yml and lab-spike.yml set `KAFKA_AUTHORIZATION=acl` and set `STACK_KAFKA_EXEC`, so the ACL test cannot skip there. Lab-spike's ACL step targets the three-bench compose.lab.yaml stack with benches `1 2 3`, which matches its broker. Shared-host rehearse runs it under `set -e`.
- Deploys keep compose.yaml and kafka/start.sh in step: deploy.sh copies the whole `config/` that setup.sh installs, so the new ready-file health check never runs against an old start.sh. The hosted default stays `none`.
- Doc links in all changed docs resolve. The `LAB_LEASE_SECONDS` ≤ 300 claim in SHARED_HOST_READINESS matches leases.ts. The capture-workbench video removal matches the deleted `tour.webm` and PLAN.md.
