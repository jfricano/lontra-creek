# Release facts: sources, ambiguities, and what the pages must not claim

September 26, 2026 · F.7 · Backs [`apps/site/src/release-facts.ts`](../../apps/site/src/release-facts.ts)

Everything below describes `streamotter@0.1.0-rc.3`, checked against the installed `node_modules/streamotter` (and `node_modules/@streamotter/*`) and the GitHub repository's public docs at tag `v0.1.0-rc.3`, fetched with `gh api -H "Accept: application/vnd.github.raw" "repos/jfricano/StreamOtter/contents/<path>?ref=v0.1.0-rc.3"`. The local StreamOtter checkout was not read.

## Sources used

- **Installed package source** (`node_modules/streamotter/`, `node_modules/@streamotter/{contracts,gateway,client}/`), specifically:
  - `@streamotter/contracts/src/{types,errors,limits,protocol}.ts` — the `ErrorCode`/`ConnectionState`/`SubscriptionState`/`Limits` types, `PUBLIC_MESSAGES`, `DEFAULT_LIMITS`, and `streamError()`.
  - `@streamotter/gateway/src/runtime/{gateway,subscription,session,traces}.ts` and `src/sources/kafka.ts` — where each `ErrorCode` is actually thrown, and the exact mechanics of the map-handler-failure case.
  - `@streamotter/client/src/{client,subscription,connection,waiters}.ts` — the browser SDK's own local error situations (`CANCELLED`, `CLIENT_CLOSED`, listener-failure `HANDLER_FAILED`).
- **Repository docs at `v0.1.0-rc.3`**: `docs/V1_API.md` (behavior, states, error vocabulary, §13's implementation refinements) and `docs/IMPLEMENTATION_STATUS.md` (the verified support matrix, Kafka modes, browser coverage, measured timings).
- **npm**: the registry API (`registry.npmjs.org/streamotter/0.1.0-rc.3`) to confirm the version is published; the website itself blocks `curl` (see below), so `NPM_RELEASE_PAGE` is asserted only to have the right shape, not fetched.

## How drift is prevented, and where it can't be

- `ErrorCode`, `ConnectionState`, `SubscriptionState`, and `Limits` are **imported types**, not copied: `ERROR_FACTS`, `SUBSCRIPTION_STATE_FACTS`, `CONNECTION_STATE_FACTS`, and `LIMIT_FACTS` are `Record<ThatUnion, …>`, so `tsc -p apps/site/tsconfig.json` fails the moment the package adds, removes, or renames a code, state, or limit key.
- `DEFAULT_LIMIT_VALUES` **is** the package's own `DEFAULT_LIMITS` object (`export const DEFAULT_LIMIT_VALUES = DEFAULT_LIMITS`), not a re-typed copy — the numbers can never disagree with the package.
- `RELEASE_VERSION` is read from `streamotter/package.json` at build time, not hand-typed, so an `npm install streamotter@<newer>` without editing this file changes `RELEASE_VERSION`/`RELEASE_TAG` immediately — which then makes every hardcoded `github.com/.../blob/v0.1.0-rc.3/...` URL in this file fail the new "every source URL points at the release tag" test, on purpose. That test failure is the intended signal that R.1 (release upgrade) needs to touch this file's sources, not just the dependency version.
- `defaultRetryable` for every `ErrorCode` is checked against `streamError(code).retryable` — the package's own default — in the test, not hand-verified once and left to rot.
- **What is *not* type-checked, and had to be hand-copied from source or docs**, because the package does not export it:
  - The `DEFAULT_RETRYABLE` map inside `@streamotter/contracts/src/errors.ts` is a private constant (not exported); only `streamError(code).retryable` exposes its values, which is what the test uses instead of importing the map directly.
  - Which handler failing produces which blast radius (source-wide pause vs. one subscription) — this is behavior, not types, so it is only verifiable by reading `runtime/gateway.ts` and `runtime/subscription.ts` and is not re-checked by any type.
  - The Kafka watchdog timing (`WATCHDOG_MS = 12_000` in `@streamotter/gateway/src/sources/kafka.ts`) is a private module constant, not exported. `TIMING_FACTS` records it by hand with `handCopied: true` and flags it for re-verification on every release upgrade.
  - The verified support matrix (Node/Socket.IO/KafkaJS/Kafka/browser versions) is prose in `IMPLEMENTATION_STATUS.md`, not a typed export; `SUPPORT_MATRIX` and `KAFKA_MODES` are hand-authored from that doc's tables.

## Ambiguities and contradictions found

1. **`IMPLEMENTATION_STATUS.md`'s own header disagrees with what's installed.** At tag `v0.1.0-rc.3`, the doc's title line still reads "V1 release candidate: `0.1.0-rc.2` on npm (`latest`); `0.1.0-rc.3` (adds the all-in-one `streamotter` package) **prepared**" — i.e., the doc committed at the `rc.3` tag describes itself as not yet published. The installed package here is genuinely `0.1.0-rc.3` (confirmed via the registry API and `node_modules/streamotter/package.json`), so the package **is** shipped; only this one status line in the doc lags the tag it's committed at. **The site must not quote that status line as current** — it should say the pinned version is `0.1.0-rc.3` (from the package itself) and cite the doc for behavior, not for "what's on npm right now."
2. **The default `retryable` flag is not one fact per code — it's situational**, and the doc and the code agree with each other but a naive reading of just the type or just `PUBLIC_MESSAGES` would miss this. Clearest example: `UNAUTHENTICATED`'s package-wide default (via `streamError("UNAUTHENTICATED").retryable`) is `true`, but every handshake-time rejection in `runtime/gateway.ts` explicitly constructs it with `retryable: false`, and session revocation does too; only an already-open session's ordinary token expiry gets `retryable: true`. `ERROR_FACTS.UNAUTHENTICATED.retryableNotes` spells this out. The same situational split exists for `INVALID_PAYLOAD` (a regressed snapshot is coded non-retryable but is actually retried by the attempt policy).
3. **"The specific operator cause" is genuinely more specific than SOURCE_UNAVAILABLE, but only for subscriptions that are *already* live or authorizing when the source goes bad.** For a subscription that begins a *new* synchronization attempt while the source is *already* paused, `subscription.ts`'s `#beginAttempt` reports `this.channel.source.reason ?? "SOURCE_UNAVAILABLE"` — i.e., it *can* see the real cause (e.g. `HANDLER_FAILED`) directly as its `stale` reason, not just `SOURCE_UNAVAILABLE`. Only the transition path (`gateway.ts`'s `#setSourceStatus`, which calls `subscription.onSourceUnavailable("SOURCE_UNAVAILABLE")` with that string **literal**) normalizes away the real cause. This is a real, verified distinction in the code, not a doc inconsistency — but it means "the visitor always sees exactly SOURCE_UNAVAILABLE" is an overstatement. The pages should describe the common case (an already-open view going stale) as SOURCE_UNAVAILABLE, per the brief's scenario, and not claim it's the *only* code a subscriber can ever see for a paused source.
4. **GitHub heading anchors cannot be verified by tooling.** `curl -sI` only checks that the *page* exists (HTTP 200), never the in-page fragment; the fragment is resolved client-side and never sent to the server. Per the brief, I instead confirmed every heading **text** referenced by an anchor genuinely exists in the raw Markdown (`docs/V1_API.md` and `docs/IMPLEMENTATION_STATUS.md`, fetched raw at the tag) and hand-computed GitHub's slug for each. One heading — "Kafka support matrix (KafkaJS 2.2.4 → Apache Kafka 4.1.2)" — has enough punctuation (parens, an arrow, two periods) that I was not confident of the exact resulting slug (single vs. double hyphen where the arrow's surrounding spaces collapse). Rather than ship a guessed anchor, `KAFKA_MODES`' sources link to `docs/IMPLEMENTATION_STATUS.md` with **no fragment**; the heading text itself is confirmed present (line 93 of the raw fetch). Every other anchor used is a plain, low-punctuation heading (e.g. "5. States and synchronization" → `#5-states-and-synchronization`) and is lower-risk.
5. **npm's website blocks plain HTTP clients.** `curl -sI` (with or without a browser `User-Agent`) returns `403` for **any** `npmjs.com/package/...` URL, including the plain, unversioned package page — this is npm's own anti-bot behavior, not a broken link. I confirmed the pinned version is actually published via the registry API instead (`registry.npmjs.org/streamotter/0.1.0-rc.3` returns the package manifest). `NPM_RELEASE_PAGE` (`https://www.npmjs.com/package/streamotter/v/0.1.0-rc.3`) follows npm's documented versioned-page URL shape; a human visiting it in a real browser will not hit this block.

## What the pages must not claim

- **Not "the visitor always sees `SOURCE_UNAVAILABLE`."** Say instead: an already-open view that goes stale because its source paused is told `SOURCE_UNAVAILABLE`, and the real cause (for example `HANDLER_FAILED`) is what the gateway's own trace shows. Don't imply the client-side code is literally unaware of the cause in every circumstance (see ambiguity 3).
- **Not "retryable" as a single flag per error code without qualification.** At minimum `/when-it-breaks` should not print a flat "retryable: yes/no" table without the caveat that a few codes (`UNAUTHENTICATED`, `INVALID_PAYLOAD`) behave differently depending on which situation produced them. `ERROR_FACTS[code].retryableNotes` exists precisely to carry that caveat where it applies.
- **Not a live trace or Failure Lab claim on the production demo gateway.** The gateway's trace (`GET /management/v1/traces`) and every other `/management/v1` route exist only on a **development-mode** gateway (`streamotter dev`, i.e. a Failure Lab bench). The production demo gateway (`streamotter start`) exposes no management routes at all. Any page showing "the trace" for the home demo is showing a Failure Lab bench's redacted feed, or a recorded/illustrated one — never the live production gateway.
- **Not any capacity or performance number as a StreamOtter claim.** The load-test numbers in `IMPLEMENTATION_STATUS.md` ("Declared workload") are the *package's* single-process, loopback measurement, explicitly "not a capacity claim" in that doc's own words. Lontra Creek's own limits (300 visitors, 12 subscriptions each, etc.) are separate, to be measured on the real host per `PLAN.md` — `SUPPORT_MATRIX`/`TIMING_FACTS` do not conflate the two, and the pages shouldn't either.
- **Not "verified" for anything this file marks `unverified` or `implemented-unverified`.** In particular: Firefox and Safari/WebKit (untested by the package's own suite — Chromium only), Kafka's system-trust TLS mode (implemented but unverified for lack of a publicly trusted broker certificate in the package's own tests), any Kafka broker version other than 4.1.2, and any managed Kafka service.
- **Not the `IMPLEMENTATION_STATUS.md` npm-publication status line as current** (ambiguity 1 above) — the pinned version is a fact from the installed package, not from that sentence.

## Three facts most likely to be misstated on a marketing page

1. **"Views are always either live or `SOURCE_UNAVAILABLE`/stale — never a specific error."** True for the browser SDK's steady-state vocabulary on an already-open subscription, but it's easy to overstate into "the client never knows the real cause," which isn't quite right (ambiguity 3), and easy to understate into implying `SOURCE_UNAVAILABLE` is retried forever with no operator step — it isn't; a paused source needs `resumeSource()`.
2. **"Every failure mode is retryable/not-retryable."** The retryable flag is a per-code *default*, and at least two codes (`UNAUTHENTICATED`, `INVALID_PAYLOAD`) have situations that override it in the shipped code. A page that prints one boolean per code without the situational caveat will be quietly wrong for those two.
3. **The verified support matrix, especially Kafka.** It is tempting to write "StreamOtter supports Kafka" unqualified. The package's own doc only verifies Apache Kafka 4.1.2 (single-node KRaft) with five specific connection modes; "other Kafka versions, managed Kafka services" are explicitly unverified, and TLS with system trust is implemented but unverified. Likewise, "browser support" must not silently promote Chromium-only testing to "supports all evergreen browsers" — the SDK is expected to work more broadly (plain WebSocket/Socket.IO, no Chromium-specific API), but the package's own verification does not cover it.
